1. REQUIREMENTS ANALYSIS
--------------------------------------------------------------------------------
Topic: Data Parallelism, Geometric Decomposition, and Performance Benchmarking.
Objective: Given an image matrix F of size n x m and a convolution kernel C of
size k x k (where k is odd, e.g., 3 or 5), calculate the resulting matrix V(n, m)
obtained by applying the 2D spatial convolution of matrix C on matrix F.

Mathematical Definition:
  For each pixel (i, j) with 0 <= i < n and 0 <= j < m, the resulting value is:
  V[i, j] = Sum_{a=0}^{k-1} Sum_{b=0}^{k-1} F[i + a - floor(k/2), j + b - floor(k/2)] * C[a, b]

Virtual Border (Clamping):
  Matrix boundaries are extended virtually using clamp-to-edge semantics:
  f[-1, j]      = f[0, j]
  f[n, j]       = f[n-1, j]
  f[i, -1]      = f[i, 0]
  f[i, m]       = f[i, m-1]
  f[-1, -1]     = f[0, 0]
  f[-1, m]      = f[0, m-1]
  f[n, -1]      = f[n-1, 0]
  f[n, m]       = f[n-1, m-1]

Laboratory Constraints & Rules:
  1. Languages: Java (Java 21) and C++ (modern C++20).
  2. Explicit Threads Only: Direct creation and management of Thread instances
     in Java and std::jthread in C++. The use of thread pools, ExecutorService,
     ForkJoinPool, or OpenMP is strictly prohibited.
  3. C++ Memory Models: Must compare two distinct allocation paradigms:
       - Dynamic Allocation: Runtime heap allocation with pointer-to-pointer (int**).
       - Static Allocation: Global compile-time fixed-capacity arrays in .bss segment.
  4. Geometric Decomposition Strategies:
       - Horizontal (Row-wise decomposition) - Base requirement.
       - Vertical (Column-wise decomposition) - Base requirement.
       - Block (2D Submatrix decomposition) - Bonus variant (+2 points).
       - Cyclic (Round-robin 1D stride delta distribution) - Bonus variant (+2 points).
  5. Measurement Discipline: Only computation time is timed; file I/O operations
     (reading matrices and writing output.txt) are strictly excluded from timing.
  6. Performance Testing: Every configuration is executed 10 times externally via
     an automated benchmark script, reporting the arithmetic mean of execution times.
     Internal function repetition loops within a single run are strictly prohibited.
  7. Correctness Verification: For every single execution (all 10 runs per test),
     the output matrix is compared element-by-element against the sequential baseline
     output_seq.txt generated from the identical input files.


2. DESIGN & SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------
Data Structures:
  - Java: Primitive 2D arrays (int[][]).
  - C++ Dynamic: Row pointer table (int**) pointing to dynamically allocated row arrays.
  - C++ Static: Flat contiguous memory array int F[MAX_N][MAX_M] placed in global
    memory (.bss segment) to prevent stack overflow on large inputs (MAX_N = MAX_M = 10005).

Core Functions & Specifications:
  1. computeConvolution(int i, int j, int n, int m, int radius):
     - Computes the convolution for a single pixel (i, j).
     - Clamps coordinates: r = clamp(i + a - radius, 0, n - 1), c = clamp(j + b - radius, 0, m - 1).
     - Time Complexity: O(k^2).

  2. computeRegion(int r0, int r1, int c0, int c1, int n, int m, int radius):
     - Applies computeConvolution across row interval [r0, r1) and column interval [c0, c1).
     - Guarantees thread isolation: no two threads write to the same element in V.

  3. getChunk(int id, int total, int p):
     - Partitions 1D index space [0, total) across p threads with optimal load balance.
     - Remainder distribution: first (total % p) threads receive (total / p + 1) elements,
       remaining threads receive (total / p) elements.
     - Formula:
         start = id * (total / p) + min(id, total % p)
         end   = start + (total / p) + (id < total % p ? 1 : 0)

  4. horizontal(int p):
     - Partitions the n rows among p threads using getChunk.
     - Each thread executes computeRegion(r0, r1, 0, m, ...).

  5. vertical(int p):
     - Partitions the m columns among p threads using getChunk.
     - Each thread executes computeRegion(0, n, c0, c1, ...).

  6. block(int p):
     - Factors p into a 2D processor grid pr x pc where pr * pc = p and pr <= sqrt(p).
     - Partitions rows into pr bands and columns into pc bands.
     - Thread (r, c) executes computeRegion(r0, r1, c0, c1, ...).

  7. cyclic(int p):
     - Implements 1D delta distribution function: delta(i, j) = (i * m + j) % p.
     - Thread id strides across flattened indices: idx = id; idx < n * m; idx += p.
     - Computes row = idx / m, col = idx % m.

  8. areEqual(int[][] A, int[][] B) / areEqual(int** A, int** B):
     - Strict verification helper verifying A[i][j] == B[i][j] for all 0 <= i < n, 0 <= j < m.


3. IMPLEMENTATION DETAILS
--------------------------------------------------------------------------------
Thread Synchronization:
  - Java: Plain Thread objects instantiated with lambda expressions. Collected in
    Thread[] workers and joined sequentially using a standard join() barrier.
  - C++: Modern C++20 std::jthread objects stored in std::vector<std::jthread>.
    std::jthread provides RAII auto-joining semantics upon vector destruction,
    eliminating manual join boilerplate and guaranteeing exception safety.

Memory Optimization:
  - In earlier iterations, a baseline matrix V_seq was allocated in all modes,
    consuming ~400 MB of heap for 10000 x 10000 matrices even during benchmark runs.
  - V_seq allocation was refactored strictly inside if (mode == "all" || mode == "verify").
    Individual benchmark modes allocate solely F, C, and V_par, saving ~400 MB RAM per run.

Build Configuration:
  - C++ standard configured to C++20 in CMakeLists.txt (CMAKE_CXX_STANDARD 20).
  - Executable targets: ConvolutionDynamic (main.cpp) and ConvolutionStatic (main_static.cpp).
  - Compilation flags: -O3 -std=c++20 with MinGW GCC 15.2.0.
  - Java: OpenJDK 21 with -Xmx8g heap allocation to prevent GC thrashing on TC5.

6. COMPARATIVE ANALYSIS & CONCLUSIONS
--------------------------------------------------------------------------------
A. Sequential vs. Parallel Performance & Amdahl's Law:
  1. Micro Workload (TC1: 10 x 10, k=3):
     - Sequential execution finishes in 0.0057 ms (C++) and 0.5542 ms (Java).
     - Parallel execution exhibits substantial slowdown (Speedup < 0.1x across all languages).
     - Explanation: Operating system thread creation, kernel scheduling, and thread joining
       impose an overhead of ~1 to 5 ms, which drastically eclipses the microscopic compute
       work of 100 elements. Parallelization is counter-productive for tiny inputs.

  2. Medium and Large Workloads (TC2 - TC5):
     - Significant parallel speedups are attained across all workloads.
     - On TC5 (10000 x 10000), C++ Static Block achieves a peak speedup of 6.21x (1175.98 ms vs.
       7302.88 ms baseline) on an 8-thread CPU!
     - Java achieves a peak speedup of 3.72x on TC5 (Block with 16 threads: 3073.55 ms vs.
       11434.53 ms baseline).

B. Comparison Between Parallel Decomposition Variants:
  1. Horizontal Decomposition (Row-wise):
     - Excels on tall and square matrices (e.g., TC4: 10000 x 10 where static horizontal reaches
       5.96x speedup).
     - Because memory is laid out in row-major order, each thread works on contiguous memory blocks,
       maximizing L1/L2 hardware prefetching and CPU cache line efficiency.

  2. Vertical Decomposition (Column-wise):
     - Dominates on wide rectangular matrices (TC3: 10 x 10000).
     - When n = 10, horizontal decomposition starves p = 16 threads (threads receive 0 or 1 row).
       In contrast, vertical decomposition divides the 10000 columns into 625 columns per thread,
       maintaining perfect thread occupancy.

  3. Block Decomposition (2D Subgrid - Bonus +2 Points):
     - Best overall decomposition for massive square matrices (TC5: 10000 x 10000).
     - Achieving 6.21x speedup in C++ Static (p=8) and 3.72x in Java (p=16).
     - Theoretical reason: A 2D block tile minimizes the perimeter-to-area ratio of the working
       submatrix, which significantly reduces cache line boundary overlap and memory bus pressure.

  4. Cyclic Distribution (Stride delta distribution - Bonus +2 Points):
     - Delivers near-perfect computational load balancing across all threads regardless of
       matrix dimensions.
     - On TC5, cyclic achieves strong speedup (4.23x in C++ Dynamic p=8, 2.35x in Java p=8).
     - However, striding by p elements causes non-contiguous memory access patterns, yielding
       slightly lower cache hit rates than contiguous block or horizontal slicing.

C. C++ Dynamic vs. Static Allocation Analysis:
  1. Contiguous Cache Layout:
     - Static allocation declares int F[MAX_N][MAX_M] as a flat compile-time block in the .bss segment.
     - Row addresses are computed via immediate multiplication (i * MAX_M + j), allowing the compiler
       to emit SIMD auto-vectorization without chasing pointer dereferences.
  2. Large Matrix Behavior (TC5):
     - C++ Static Sequential completes in 7302.88 ms vs. 10544.20 ms for C++ Dynamic Sequential
       (Static is ~30% faster sequentially).
     - Under multithreading, C++ Static Block hits 1175.98 ms (6.21x speedup), outperforming all variants.
  3. Narrow Matrix Behavior (TC4: 10000 x 10):
     - In static allocation, each row occupies MAX_M = 10005 integers (40 KB stride).
     - Moving to the next row incurs a cache line miss because the next row is 40 KB away.
     - Dynamic allocation allocates each row with exact capacity m = 10 (40 bytes), keeping
       successive rows packed closer in heap pages. Thus, Dynamic is faster on TC4.

D. Java vs. C++ Execution Speed:
  - C++ consistently outpaces Java across all test cases:
    * TC2 Sequential: C++ Dynamic = 48.27 ms vs. Java = 78.25 ms (~1.6x faster).
    * TC5 Sequential: C++ Static = 7302.88 ms vs. Java = 11434.53 ms (~1.6x faster).
    * TC5 Parallel Peak: C++ Static = 1175.98 ms vs. Java = 3073.55 ms (~2.6x faster).
  - The C++ performance superiority arises from aggressive -O3 optimizations (loop unrolling,
    AVX2 vectorization), zero runtime array bounds checking, and direct cache line control
    without JVM garbage collector pauses.
