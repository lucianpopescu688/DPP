1. REQUIREMENTS & PROBLEM FORMULATION
--------------------------------------------------------------------------------
Given an input image matrix F(N, M) from "date.txt" and a convolution kernel C(k, k)
from "ConvolutionM.txt" (randomly generated by generateMatrices.ps1, with fallback
to a standard 3x3 sharpening kernel if absent):

The objective is to compute the filtered matrix directly IN-PLACE inside the
original matrix memory, adhering to strict laboratory constraints:
- Input Data: Read from "date.txt" (N x M) and "ConvolutionM.txt" (k x k).
- Postcondition: The initial matrix memory must contain the filtered image.
- Memory Constraint: NO result matrix and NO temporary full matrix of size O(N x M).
  Only 1D temporary row vectors within O(M) auxiliary space per thread are allowed.
- Border Policy: Outer border pixels (i = 0, i = N-1, j = 0, j = M-1) are preserved.
- Threading: Explicit thread primitives only (std::jthread in C++26,
  java.lang.Thread with Runnable in Java 25). No thread pools or executors.
- Concurrency Coordination: Barrier synchronization (std::barrier in C++26,
  java.util.concurrent.CyclicBarrier in Java 25).
- Benchmarking Rules: Arithmetic mean of 10 external program executions.
- Verification: Every run output is verified element-by-element against output_seq.txt.


2. ARCHITECTURE & IN-PLACE DECOMPOSITION STRATEGY
--------------------------------------------------------------------------------
In standard 2D convolution, each output pixel V[i, j] depends on F[i-1..i+1, j-1..j+1].
Overwriting F[i, j] in-place introduces write-after-read hazards across neighboring rows.
To resolve this with strictly O(M) auxiliary memory per thread:

1. Horizontal Row Partitioning:
   - Rows are partitioned across P threads: [start_row, end_row).
2. Phase 1 - Local Compute & Direct Interior Commit:
   - Intermediate interior rows (start_row < i < end_row - 1) are written directly
     into matrix[i], as no neighbor thread reads them.
   - Boundary rows (start_row and end_row - 1) are buffered into 1D arrays
     (new_top, new_bottom), leaving original matrix rows intact for neighbors.
3. Phase 2 - Global Synchronization Barrier:
   - All P threads wait at the barrier (std::barrier / CyclicBarrier) ensuring
     all reads are complete.
4. Phase 3 - Boundary Commit:
   - Each thread writes its new_top and new_bottom into the matrix.

Space Complexity: O(P x M) total auxiliary RAM across all threads vs O(N x M)
for a full matrix copy. On 10,000 x 10,000, auxiliary memory is reduced from
~400 MB to ~1.3 MB (>300x reduction).

5. COMPARATIVE ANALYSIS & TAKEAWAYS
--------------------------------------------------------------------------------
1. In-Place Memory Efficiency:
   Barrier-synchronized delayed boundary writing (Variant 2B) completely eliminates
   the need for an auxiliary N x M matrix, enabling processing of 100M-element matrices
   with only ~1.3 MB RAM instead of ~400 MB.
2. Barrier Scalability:
   Only boundary rows are delayed; all interior rows commit concurrently in Phase 1.
   Barrier overhead is negligible (< 0.1% of runtime on large matrices).
3. Core Scaling:
   Peak speedup is achieved at p = 4 threads (~2.78x in C++, ~2.70x in Java),
   matching the 4 physical CPU cores of the AMD Ryzen 7 3750H. Oversubscription
   at p = 16 introduces context switching penalties.
4. C++ vs. Java:
   C++26 is ~15-20x faster than Java due to raw pointer arithmetic, compiler
   SIMD vectorization (-O3), and absence of JVM runtime overhead.
